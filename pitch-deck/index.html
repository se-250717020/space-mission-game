02 / The problemSpace Mission Designer

Space missions are all about trade-offs

But in class, students usually only see the launch.

  • 🧩

    The engineering is invisible

    Every real mission balances money, mass, power, radiation and data. Those decisions rarely reach a classroom.

  • 📖

    Facts without the “why”

    “Sunlight at Saturn is 90× weaker” is just a number to memorize — until your own spacecraft runs out of power.

  • 🧪

    Nothing in between

    Space games are mostly just for fun, and real mission tools are made for experts. Kids need a place to make real choices and see what happens.

Mission check
💰 Money Money left over
🏋️ Weight Rocket is straining
⚡ Power Not enough power!
☢️ Radiation Safe

Change one part, and everything else moves. That is mission design.

Real missions are a web of trade-offs: a bigger antenna adds mass, more power costs money, a far target needs a stronger rocket. Students rarely get to make those choices themselves.

04 / Space School · NASA dataSpace Mission Designer

NASA missions behind every number

Space School explains each choice as you make it, using facts from real missions.

Example: why not solar at Saturn?

  1. ☀️At Saturn, sunlight is 90× weaker than on Earth.
  2. 🔴Solar panels can’t keep up, so the POWER check turns red.
  3. ☢️Fix it with a nuclear battery (RTG). It works even in the dark.
  4. 💰But it costs more. Every choice is a trade-off.

Rule 1

One source of truth

The UI does no math. Every number comes from calculations.py.

Rule 2

Tested before every commit

Schema check, calculation self-tests and a production build.

Rule 3

One container, one URL

Docker builds the React app; FastAPI serves it next to /api on Render.

data.py holds only data, calculations.py holds all the rules and physics as pure functions, FastAPI exposes them as a JSON API, and React only draws. Because the UI does no math, every number on screen is consistent and tested. One Docker container serves both the game and the API.
